Using knowledge graphs to check what an LLM says

Four tests. Two worked, one failed against a pass/fail line set in advance, and four earlier results were withdrawn under audit.

7 August 2026

The question

There is a great deal of structured graph and ontology data sitting in enterprises. Can it be used to verify that what an LLM generates is not complete bullshit?

Not to train the model. Not to align it. Not to make it reason. To check its output against something already known to be true.

Result

Catch the model naming things that do not exist Yes. 56 of 100 invented query routes caught. Invented property names 69 per 100 → 0. Zero false alarms — if the graph says it exists, it exists.
Confirm the answer is correct No. Of 44 answers that passed the check, 33 were still wrong. A 75% false-assurance rate among passes.
Work with no training or fine-tuning Yes. Runtime only. Nothing is learned, nothing is retrained.
Work where the graph doesn't cover the question No. Blind on 7% of questions — and a check that passes because it is blind is worse than no check.

“Is X in the graph” is a decidable question. Entailment models, LLM judges and self-consistency all guess, and all produce false alarms. This does not.

Generated text cannot name an entity, property or relationship that is absent from your governed data. Checked exactly, no model in the loop, no false alarms. It does not check that the claim about those entities is true.

What was measured

Both sides hold identical information — the search corpus is the same facts written out as sentences. Only the access method differs. But tell the model only how many answers it missed, never which, and 76 becomes 9. Two thirds of that score is the model repeating names placed in its prompt. The graph did the work; the language model barely participated.

Search wins outright. “What properties does this class have” is a lookup, and search finds the file. We expected the graph to win and it did not.

The same models, asked as a traversal

out of 100 routesPlain LLMOrdinary searchWith the graph
routes written that do not exist 99561

Given the starting class outright, search still wrote a route that does not exist 56 times out of 100 — hideTaggedValues.taggedValues, name.nullable. That number is measured against the graph with no answer key involved. The graph column here is a database walk with no language model in it at all.

Enterprise documents — failed

Before running it we wrote the pass/fail line into the repository, including “we do not re-cut the data by category, swap the primary metric, or expand the sample looking for a favourable slice.”

Result: +0.008, confidence interval −0.009 to +0.025. It includes zero. By our own written rule, the idea is not supported on enterprise documents. Two known defects cause it; neither is fixed.

What we stopped

Cross-attention injection of graph memory Built, trained fifteen epochs, moved accuracy by +0.002.
Building a graph from company prose Scored −0.12 against the very documents it was built from.
Competing on published benchmarks Established systems score 78, 91 and 95 on the same movie questions. We are last, and it is a solved problem.
Calling any of this reasoning It is a text-to-query engine over a graph. That framing is defensible; the other was not.

What held throughout

Nothing was ever made worse. Across every test, both models, every setting: not one answer that was right beforehand came out wrong afterwards. That is a property of the constraint rather than of anything clever, and it is the only claim that never needed qualifying.

Where this goes

Two things are worth keeping. The rest should stop.

  1. The constraint itself — about 180 lines. It makes it impossible, not merely unlikely, for a model to write an identifier that is not in your data. Against a plain model that is a 69-point reduction; against ordinary search it is under half a point. The value is not the size of the reduction — it is that search's near-zero has no floor and this zero is structural. A bank cannot write “rarely names a nonexistent counterparty” in a control document. It can write “cannot.”
  2. The measurement discipline — pre-registered pass/fail lines, paired comparisons, exact scoring with no AI marking the work. In a single day it found four fatal flaws in our own results, including one that made a headline number meaningless.

The natural customer is an organisation that already maintains a knowledge graph or semantic model, because the one thing we could not do is build the graph. The integration surface is a single function: given a question, return the entities the graph will vouch for. Everything upstream stays where it is.

Every figure comes from a saved per-question record; each test re-runs from one command. Full detail, including the four withdrawn results, in POC.md.
