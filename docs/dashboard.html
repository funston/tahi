TAHI — an overview

Language models make things up. TAHI puts a knowledge graph in the way, so the model can't name anything the graph doesn't contain.
We compared three things on three problems. The results point in opposite directions depending on the kind of question, and that's the interesting part.

Corrections after an outside review, 2026-08-07. An independent audit found three real problems. All are now reflected below rather than argued with.

1. On the movie test, the correction step was naming the missing answers in the prompt. We re-ran it with the names withheld — telling the model only how many it had missed. The score fell from 76 out of 100 to 9. So 67 of those points were the model copying an answer it had been handed. The graph found the answer; the language model did not reason its way to it.

2. On the Legend routing test, TAHI's arm calls no language model at all — it is a Python graph walk. We had already withdrawn the accuracy figure; the validity figure carries the same caveat and now says so.

3. We ran an enterprise test earlier with a written-down pass/fail line agreed before the run. It failed. That was missing from this page and is now included below.

The three things being compared

Plain LLM — the model answers on its own. Nothing added.

RAG — the usual approach. Search for relevant material, paste it into the prompt, let the model answer.

TAHI — look the facts up in a knowledge graph, then tell the model only what it got wrong and make it answer again. It can't name anything the graph doesn't have.

Test 1 — MetaQA

A public set of movie questions. 134,741 facts about films. 14,274 questions the system had never seen. Each needs three facts chained together.

Plain LLM

1 out of 100 questions answered correctly

RAG

2 out of 100 questions answered correctly

TAHI

78 out of 100 questions answered correctly

“Which person wrote the movies directed by the director of Scott of the Antarctic?”

Plain LLM
(nothing — it doesn't know)
RAG
ivor montagu, mary hayley bell, walter meade
TAHI
eric ambler, nicholas monsarrat
Truth
eric ambler, nicholas monsarrat

RAG's answer isn't gibberish — those are real screenwriters. They're just the wrong ones. It found documents about the film and guessed. Nothing in the answer looks wrong, which is exactly the problem.

But read the TAHI row carefully. The graph lookup produced eric ambler, nicholas monsarrat and the correction step put those names into the prompt. The model then repeated them. Withhold the names and the score drops to 9 out of 100. This is a graph query with a language model translating the question — not a language model reasoning better.

Test 2 — Legend, asked as a lookup

Goldman Sachs' data modelling platform, open-sourced and now run by FINOS. Its models describe a business: a Firm has a legalName and employees. We read 883 of their classes straight from the public repository — no guessing, just reading files.

The question: “what properties does this class have?” That is a lookup. The answer sits in one file.

Plain LLM

0 out of 147 classes listed correctly

RAG

133 out of 147 classes listed correctly

TAHI

0 out of 147 classes listed correctly

“What properties does the class COVIDData have?”

Plain LLM
id, name, date, confirmed_cases, recovered_cases, deaths
RAG
id, fips, date, caseType, cases, lastReportedFlag
TAHI
id, name, date, cases, tests, location
Truth
caseType, cases, date, demographics, fips, id

RAG wins outright. Search finds the file, the file has the answer. TAHI stopped the model inventing names but every name it picked was still the wrong one. We expected TAHI to win here and it didn't.

Test 3 — Legend, asked as a traversal

The same 883 classes, but this is what Legend actually does when you query it. A Legend GraphQL query is a walk through the model — firm { employees { firstName } } hops from Firm to Person and then reads a value. Two steps, through two different classes.

The question: given a starting class and a value you need, what is the route? The middle step is never named.

Plain LLM

99 out of 100 routes it wrote do not exist

RAG

56 out of 100 routes it wrote do not exist

TAHI

1 out of 100 routes it wrote do not exist

Starting from ColumnPtr, reach the value called schema. What is the route?

Plain LLM
a route that doesn't exist
RAG
tableAlias.schema
TAHI
table.schema
Truth
table.schema

Even when handed the starting class's definition outright, RAG wrote a route that doesn't exist 56 times out of 100 — hideTaggedValues.taggedValues, name.nullable. When the route did exist it was usually still the wrong one: tableAlias is a real property sitting next to the correct one in the retrieved text.

What this test does NOT prove, and why. We first reported TAHI at 99 out of 100 for finding the exactly-right route. That number was worthless and we have removed it. The questions were filtered to those with exactly one possible route, and TAHI answers by listing the routes — so it was re-deriving the answer key with the same code that wrote it. A tautology, not a measurement.

The first version was worse still: the retriever surfaced the class holding the answer only 3 times out of 100, so RAG could not have won at all. It has since been handed the starting class outright, which is what a real system would do.

And TAHI's column here involves no language model at all. It is a Python graph walk. Comparing it to two arms that do use a model is comparing a database lookup to a guess. Worth knowing which is which.

What survives is the RAG number: handed the starting class outright, it still wrote a route that does not exist 56 times out of 100. Nothing about the answer key is involved in that measurement — the model writes something, the graph says yes or no.
Same model, same files, opposite results. Ask Legend a lookup question and search wins 133 to 0. Ask it a routing question and search writes a route that doesn't exist more than half the time. It is the question type that decides, not the data.

A fourth test, which TAHI failed

Before running it we wrote down, in the repository, the line that would count as failure — so it could not be moved afterwards:

“If tahi − rag on the primary measure has a 95% confidence interval that includes zero at n=170, the structural thesis is not supported on enterprise multi-source questions. We publish that, and we do not re-cut the data by category, swap the primary measure, or expand the sample looking for a favourable slice.”
— benchmarks/PREREGISTRATION_enterprise_rag.md, written before the run

The result on 170 questions: +0.008, confidence interval −0.009 to +0.025. It includes zero. TAHI did not beat ordinary search on enterprise documents, and by our own written rule that means the idea is not supported there.

Two known causes, both with failing tests in the repository that document them: the graph edges were never actually used to find candidate documents, and non-document entries crowded documents out of the results. Neither has been fixed.

The other measurement: names it made up

Separately from whether the answer is right, we counted how many of the names each system wrote down don't exist at all — no such film, no such property.

Plain LLMRAGTAHI
MetaQA — made-up names, out of every 100 written 1200
Legend — made-up names, out of every 100 written 690.40

On its own the model invents constantly. Give it real material to work from and it mostly stops. TAHI takes it to exactly zero — but so does RAG, nearly.

What we actually learned

1 — Following links beats searching text, when the question needs several steps. The movie questions need three facts chained. Search over the same information gets 2 out of 100. A graph query gets 78. That comparison is real and it is about retrieval, not about intelligence.
2 — But the language model is doing almost none of it. Take the answers out of the correction prompt and the score falls from 76 to 9. What we built is a graph query engine that uses a language model to turn the question into a query. That is a legitimate thing to build. It is not a language model reasoning better because it has a graph, and we should never have let the page imply otherwise.
3 — When the question is a lookup, use ordinary search. “What properties does this class have” is answered by finding the file: search gets 133 out of 147 and TAHI gets 0.
4 — On real enterprise documents it did not work at all. It failed a pass/fail line we wrote down in advance. Two known defects cause it and neither is fixed.
5 — It never made an answer worse. Across every test: not one answer that was right beforehand came out wrong afterwards. That much has held throughout.

What this doesn't show

The movie facts were handed to usThey came with the test, already correct. A real company has to build that graph from its own documents, and when we tried that on ordinary business writing the result was worse than useless. Legend sidesteps this because the model is already written down — most companies aren't Legend.
The Legend test isn't a benchmarkWe wrote the question and picked the classes. Nobody else runs it and there's nothing to compare against.
We tell it where to startBoth tests hand the system the entity or class the question is about. Working that out from the question is a separate problem we haven't touched.
One in five can't be reachedOn 21 out of every 100 movie questions the graph lookup can't reach the right answer at all. Nothing recovers those.
We're not near the best systemsPublished results on the same movie questions: 78, 91, 95 out of 100. We're at 78.
Everything ran onceSingle run of 100 or 147 questions. No repeats.
